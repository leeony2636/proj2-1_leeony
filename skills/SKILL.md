# 방탈출 힌트 판단 Skill

> **현재 적용 상태 (2026-09-22.v3)**  
> 이 문서는 현장 경험과 과거 판단 기준을 보존하는 원본 Skill 기록이다. 실제 LLM 입력에는
> `skills/domain_policy.json`에서 현재 적용 대상으로 분리한 **확정 경계 + 현장 판단 참고 기준**만 전달한다. v3에서는 위치 혼동 지원 기준과 문제 번호/전체 문제 수 비공개 경계를 compact policy에 명시적으로 연결했다.
> 아래의 `남은 시간 15분/남은 문제 비율 50%` 숫자 규칙과 `재요청 자동 STRONG 승격`은
> 팀 최종 확정이 확인되지 않아 현재 실행 정책으로 사용하지 않는다. 삭제하지 않고 팀 결정 대기 항목으로 보존한다.

> 필수 조건 5 — 도메인 지식과 판단 기준을 여기에 적어 모델에 넘깁니다.
> 검색해서 그때그때 넣는 방식(RAG)과 LangGraph는 이 프로젝트에서 사용하지 않습니다.

## 이 도메인은 무엇을 다루나

방탈출 손님이 게임 진행 중 막혔을 때, 게임마스터(진행자) 없이 Agent가 힌트 제공 여부와 강도를
판단하는 도메인이다. 실제 매장에서는 진행자가 여러 방을 동시에 모니터링하며 손님의 발화·타이머·
진도를 보고 힌트를 줄지, 준다면 약한 힌트(위치만 안내)인지 강한 힌트(풀이 과정 설명)인지를 그 자리에서
판단한다. 이 판단은 매뉴얼로 완전히 커버되지 않고, 진행자 개인의 경험과 감으로 메워지는 부분이 크다.

이 Skill은 그 판단 기준을 Agent에 넘기기 위한 도메인 지식이다. 손님이 정답을 직접 요구하는 상황,
기구 이상을 답답함으로 오인하는 상황 등 실제 현장에서 반복됐던 문제 상황과, 그때 실제로 어떤
판단이 맞았는지(혹은 틀렸는지)를 기준으로 정리했다.

## 용어

| 용어 | 뜻 | 주의 |
|---|---|---|
| 약한 힌트 | 문제 위치만 안내 | 풀이 방법은 설명하지 않음 |
| 강한 힌트 | 풀이 과정을 설명 | 정답 그 자체는 아님. 화면 안에 정답 확인 경로가 함께 표시됨 |
| 정답 확인 | 자물쇠 번호 등 정답 자체를 공개하는 것 | 강한 힌트 화면 안의 별도 경로(탭)로만 노출. Agent가 먼저 말로 꺼내지 않음 |
| 재요청 오버라이드 | 약한 힌트 제공 후 짧은 시간 내 같은 문제로 재요청 시 강한 힌트로 자동 승격 | 다른 문제에 대한 재요청은 해당 안 됨 |
| 감정 오버라이드 | 손님 발화에서 강한 좌절/무력감이 감지되면 시간·진도 조건 무시하고 강한 힌트로 승격 | 애매한 혼잣말 수준은 발동 안 함(아래 판단 기준 참고) |
| 남은 문제 비율 | 남은 문제 수 ÷ 전체 문제 수 (remaining_puzzle_ratio) | 문제 번호가 아니라 비율로 통일(테마마다 문제 수가 다르므로). 해결한 비율이 아니라 "남은" 비율 기준 |
| 문제 번호(puzzle_id) | 내부 관리용으로만 쓰는 식별자 | 손님에게 절대 노출하지 않음. 아래 "하지 말아야 할 것" 참고 |

## 판단 기준

1. **우선순위는 정답 요구 → 재요청 오버라이드 → 감정 오버라이드 → 기본규칙 순으로 확인한다.**
   기본규칙(남은시간 ≤ 15분 AND 남은 문제 비율 ≥ 50% → 강한 힌트, 그 외 → 약한 힌트)보다
   정답 요구·재요청·감정 신호가 먼저 적용된다. 이 셋 중 아무것도 해당하지 않을 때만
   기본규칙으로 판단한다.

2. **감정 오버라이드는 "시간·시도 경과 언급 + 무력감"이 함께 있을 때만 발동한다.**
   단순히 "모르겠어요"라는 표현만으로는 부족하다. 실제로 강한 감정으로 봐야 했던 발화는
   다음 두 요소가 같이 나타났다:
   - 시간이나 반복 시도가 언급됨 ("10분 동안 풀었는데", "아까부터")
   - 포기/무력감이 드러남 ("모르겠어", "시도도 못하겠어")

   예: "10분동안 풀었는데 진짜 너무 모르겠어" / "아예 시도도 못하겠어, 어떻게 해야해"
   → 강한 힌트로 즉시 승격.

   반대로 단순 위치 파악 실패는 감정 강도가 세 보여도 약한 힌트로 충분할 수 있다.
   예: "무슨 서랍인지 모르겠다고" → 위치 안내(약한 힌트)로 우선 대응, 그래도 반복되면 재요청
   오버라이드가 자연스럽게 승격시킨다.

3. **정답 직접 요구는 시간·진도 조건과 무관하게 즉시 강한 힌트로 응답한다.**
   손님이 "그냥 정답 줘"라고 직접 요구하면, 기본규칙(남은시간·남은 문제 비율)을 확인할 필요 없이
   바로 강한 힌트(풀이 과정 설명)로 응답한다. 강한 힌트 화면에는 손님이 원하면 직접 눌러
   확인할 수 있는 별도의 "정답 확인" 경로(탭 형태)가 포함된다. 단, Agent는 정답을 먼저
   말로 꺼내주지 않는다 — 손님이 그 경로를 직접 열어야만 정답이 보인다.
   (이유는 아래 "예외와 함정" 참고)

4. **진도는 우선 발화로 추정하고, 모호할 때만 직접 확인 질문을 던진다.**
   현장에서는 진행자가 CCTV로 볼 때도 있었지만, 여러 방을 동시에 볼 때는 놓치기 쉬워
   웬만하면 손님에게 "지금 어떤 문제 풀고 계세요?"라고 직접 물어 진도를 확인했다.
   Agent는 사람이 아니라서 매번 직접 물으면 대화가 번거로워지므로, 우선 손님의 자연어
   발화를 테마별 문제 내용과 대조해 스스로 진도를 추정한다. 그래도 진도 표현이 모호하면
   "마지막으로 푼 문제가 무엇인지"를 직접 확인 질문으로 던진다 — 현장에서도 결국
   직접 물어보는 것이 가장 정확한 방법이었다.

## 예외와 함정

- **"안 열리네", "왜 안 열려요" 류의 발화는 답답함이 아니라 기구 이상 신호일 수 있다.**
  겉으로는 힌트 요청처럼 보이지만, 실제로는 자물쇠 오작동이나 소품 이상인 경우가 많다.
  이런 발화는 감정 판단보다 먼저 원인부터 구분해야 한다: 정답 오류 / 자물쇠 오인 / 사용법 미숙 /
  실제 기구 이상. 기구 이상으로 판단되면 힌트가 아니라 즉시 게임마스터 호출(MASTER_REQUEST)로
  전환한다.

- **정답 요구에 진행자가 "말로" 직접 답해주면 문제가 된다.**
  현장에서 정답을 말로 직접 알려준 경우, 실제로 매니저에게 반복적으로 지적받았다.
  손님이 문제를 풀어 얻는 성취감이 게임의 핵심 가치인데, 진행자가 먼저 정답을 불러주면
  그 경험 자체가 사라지고 손님 만족도도 오히려 떨어진다. "웬만하면 정답을 줬다"는 것은
  진행자가 매번 말로 알려주며 편하려 했던 잘못된 관행이었다. 다만 정답 확인 자체를
  아예 막는 것은 해결책이 아니었다 — 그래서 매장은 "손님이 스스로 여는 탭"으로
  정답 확인 경로를 분리해, 진행자가 직접 불러주지 않으면서도 손님이 필요하면 확인할 수
  있게 했다.
  → Agent도 이 방식을 따른다: 정답을 답변 텍스트에 먼저 꺼내 말하지 않고, 손님이
  직접 여는 별도 액션으로만 노출한다.

- **정답 요구·재요청·감정 오버라이드가 동시에 겹칠 수 있다.**
  예를 들어 약한 힌트 직후 재요청하면서 동시에 좌절 표현을 쓰는 경우, 어느 조건으로 봐도
  결론은 똑같이 강한 힌트다. 이런 경우 결론이 같다고 조건을 아무거나 적당히 갖다 붙이지
  말고, 실제로 어떤 조건이 있었는지(정답 요구였는지, 재요청이었는지, 감정 표현이었는지)를
  정확히 구분해서 남겨야 한다. 나중에 이 판정이 맞았는지 틀렸는지 되짚어볼 때, 조건이
  뭉뚱그려져 있으면 어디를 고쳐야 할지 알 수 없다.

## 하지 말아야 할 것

- **정답(자물쇠 번호, 해답)을 응답 텍스트에 먼저 말로 꺼내지 않는다.** 정답 요구가 오면
  강한 힌트로 즉시 응답하되, 정답 자체는 손님이 직접 여는 별도 확인 액션(탭)으로만
  노출한다. Agent가 먼저 "정답은 OOO입니다"라고 말하지 않는다.
- **감정 표현만 보고 섣불리 판단하지 않는다.** "모르겠다"는 표현 하나만으로 강한 힌트로 승격하지
  않는다. 시간·반복 시도 언급이 함께 있는지 반드시 같이 본다.
- **기구·소품 이상 의심 상황을 힌트로 대응하지 않는다.** "안 열린다", "이미 풀려있다" 같은 발화는
  힌트 판단 이전에 원인부터 구분하고, 실제 이상이 의심되면 즉시 게임마스터에게 넘긴다.
- **다른 테마의 문제나 힌트를 조회하거나 노출하지 않는다.** 세션 시작 시 고정된 테마 데이터만
  조회하도록 강제한다.
- **아직 도달하지 않은 순서의 문제에 대한 질문에 먼저 답하지 않는다.** 스포일러 방지를 위해
  순서부터 안내한다.
- **문제 번호나 전체 문제 개수를 손님에게 직접 알려주지 않는다.** 문제 번호(순서)를 알면
  그 순서대로 찾아서 풀 수 있게 되어 탐색·추리의 재미가 사라진다. "몇 번째 문제인지",
  "이 테마는 총 몇 문제인지"는 내부 관리용 정보이며, 힌트 응답에는 문제 번호 없이
  힌트 내용만 담아 전달한다. 진도 확인이 필요할 때도 손님에게는 "지금 하고 있는 문제"
  식으로만 언급하고 번호를 말하지 않는다.
