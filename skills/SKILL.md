# 방탈출 힌트 판단 Skill

> 현재 적용 상태 (2026-09-22.v3): 이 문서는 현장 경험과 과거 기준의 원본 기록이다.
> 실제 LLM 입력에는 `skills/domain_policy.json`의 확정 경계와 판단 참고 기준만 전달한다.
>
> **읽는 규칙**: 아래 "판단 기준" 표의 모든 행에는 서로 다른 두 축이 따로 표시된다.
> - **상태**: 이 규칙을 쓰기로 했는가 — ✅ 확정 / 🚫 검토 후 미채택. 이 값만 강의(13강 할루시네이션과
>   근거요구)가 말하는 "확정/미확정" 2분법과 대응한다.
> - **구현**: 확정된 규칙이 실제 `domain_policy.json`·코드에 들어가 있는가 — 구현됨 / 미구현.
>   "미채택"인 규칙은 애초에 구현 대상이 아니므로 이 칸은 해당 없음(—)으로 둔다.
>
> 두 축을 하나로 합치지 않는다 — "미채택"과 "미구현"은 원인이 다른 별개의 질문이다.
> `domain_policy.json` 매핑 id가 함께 있다. 상태 표시가 없는 문장은 이 문서의 결함이니 발견 즉시 표로 옮겨야 한다.
> 본문 서술과 상태 표가 어긋나면 **표가 우선**이다 — 서술은 표의 부연 설명일 뿐이다.

> 필수 조건 5 — 도메인 지식과 판단 기준을 여기에 적어 모델에 넘깁니다.
> 검색해서 그때그때 넣는 방식(RAG)과 LangGraph는 이 프로젝트에서 사용하지 않습니다.

## 이 도메인은 무엇을 다루나

방탈출 손님이 게임 진행 중 막혔을 때, 게임마스터(진행자) 없이 Agent가 힌트 제공 여부와 강도를
판단하는 도메인이다. 실제 매장에서는 진행자가 여러 방을 동시에 모니터링하며 손님의 발화·타이머·
진도를 보고 힌트를 줄지, 준다면 약한 힌트(위치만 안내)인지 강한 힌트(풀이 과정 설명)인지를 그 자리에서
판단한다. 이 판단은 매뉴얼로 완전히 커버되지 않고, 진행자 개인의 경험과 감으로 메워지는 부분이 크다.

이 Skill은 그 판단 기준을 Agent에 넘기기 위한 도메인 지식이다. 손님이 정답을 직접 요구하는 상황,
기구 이상을 답답함으로 오인하는 상황 등 실제 현장에서 반복됐던 문제 상황과, 그때 실제로 어떤
판단이 맞았는지(혹은 틀렸는지)를 기준으로 정리했다.

## 용어

| 용어 | 뜻 | 상태 | 매핑 id | 주의 |
|---|---|---|---|---|
| 약한 힌트 | 문제 위치만 안내 | ✅ 확정 | — | 풀이 방법은 설명하지 않음 |
| 강한 힌트 | 풀이 과정을 설명 | ✅ 확정 | — | 정답 그 자체는 아님. 화면 안에 정답 확인 경로가 함께 표시됨 |
| 정답 확인 | 자물쇠 번호 등 정답 자체를 공개하는 것 | ✅ 확정 | `ANSWER_TEXT_GUARD` | 강한 힌트 화면 안의 별도 경로(탭)로만 노출. Agent가 먼저 말로 꺼내지 않음 |
| 재요청 오버라이드 | 약한 힌트 제공 후 짧은 시간 내 같은 문제로 재요청 시 **자동으로** 강한 힌트 승격 | 🚫 검토 후 미채택 | `AUTO_REREQUEST_ESCALATION` | 자동 승격 대신, LLM이 힌트 이력을 조회해 재요청 발화의 의미를 함께 보고 판단한다 |
| 감정 오버라이드 | 손님 발화에서 강한 좌절/무력감이 감지되면 강한 힌트로 승격 | ✅ 확정 | `FRUSTRATION_CONTEXT` | 애매한 혼잣말 수준은 발동 안 함(아래 판단 기준 참고) |
| 남은 문제 비율 | 남은 문제 수 ÷ 전체 문제 수 (remaining_puzzle_ratio) | 🚫 검토 후 미채택 | — | 관측용 메타데이터로만 기록됨(`hint_policy.py`). 힌트 강도 자동 계산에는 쓰이지 않음 |
| 문제 번호(puzzle_id) | 내부 관리용으로만 쓰는 식별자 | ✅ 확정 | `PUZZLE_POSITION_METADATA_PRIVATE` | 손님에게 절대 노출하지 않음. 아래 "하지 말아야 할 것" 참고 |

## 판단 기준

| # | 판단 기준 | 상태 | 구현 | domain_policy.json 매핑 | 비고 |
|---|---|---|---|---|---|
| 1 | 정답 직접 요구는 시간·진도와 무관하게 즉시 강한 힌트로 응답 | ✅ 확정 | 구현됨 | `ANSWER_TEXT_GUARD` + `hint_policy.py` 매핑 로직 | 최우선순위 |
| 2 | 감정 오버라이드는 "시간·시도 경과 언급 + 무력감"이 함께 있을 때만 발동 | ✅ 확정 | 구현됨 | `FRUSTRATION_CONTEXT` | 단순 "모르겠어요"만으로는 발동 안 함 |
| 3 | 위치 파악 실패는 감정 표현이 세도 곧장 강한 지원으로 확대하지 않음 | ✅ 확정 | 구현됨 | `POSITION_CONFUSION_SUPPORT` | 위치 안내(약한 힌트) 우선 고려 |
| 4 | 장비·소품 이상 신호는 단정하지 않고 원인부터 구분 | ✅ 확정 | 구현됨 | `EQUIPMENT_AMBIGUITY` | 정답오류/자물쇠오인/사용법미숙/실제이상 구분 |
| 5 | "아까/그거/아직" 같은 후속 표현은 이력·상태 조회로 연결해 판단 | ✅ 확정 | 구현됨 | `FOLLOWUP_CONTEXT` | 재요청도 이 경로로 LLM이 의미 판단 (자동 규칙 아님) |
| 6 | 독립 복합 요청인지 불명확하면 부작용 실행 전에 확인 질문 | ✅ 확정 | 구현됨 | `CLARIFY_WHEN_NEEDED` | |
| 7 | 직원 전달은 사실·시도·미확인을 구분하고 원인·긴급도를 추측하지 않음 | ✅ 확정 | 구현됨 | `STAFF_HANDOFF_FACTS` | |
| 8 | 진도는 발화로 우선 추정하고, 모호할 때만 직접 확인 질문 | ✅ 확정 | 구현됨 | `PROGRESS_INFERENCE_THEN_CLARIFY` | 원래 SKILL.md에만 있고 누락돼 있던 것을 `llm_guidance`에 추가함 |
| — | 숫자 기반 힌트 강도 규칙(15분/50%) | 🚫 미채택 | — (미채택이라 구현 대상 아님) | `NUMERIC_HINT_STRENGTH_RULE` | 의미 판단 중심(A안)으로 확정, 이 규칙은 검토 후 안 쓰기로 함 |
| — | 재요청 자동 STRONG 승격 | 🚫 미채택 | — (미채택이라 구현 대상 아님) | `AUTO_REREQUEST_ESCALATION` | 검토 후 안 쓰기로 함, 대신 #5 경로로 LLM이 판단 |

`domain_policy.json`에는 미채택 두 항목도 `unconfirmed_policies` 배열에 `DECIDED_NOT_ADOPTED`
상태로 남아있다 — 자동 실행 기준에서 제외한다는 코드 계약(`test_domain_agent_followup.py`)이
이 배열의 존재 자체에 걸려 있어서, 값을 지우지 않고 상태만 "결정됨"으로 표시했다.

### 판단 기준 부연 설명

**#2 감정 오버라이드**: 실제로 강한 감정으로 봐야 했던 발화는 다음 두 요소가 같이 나타났다 —
시간이나 반복 시도가 언급됨("10분 동안 풀었는데", "아까부터") + 포기/무력감이 드러남("모르겠어",
"시도도 못하겠어"). 반대로 단순 위치 파악 실패는 감정 강도가 세 보여도 약한 힌트로 충분할 수 있다.

**#8 진도 추정**: 현장에서는 진행자가 CCTV로 볼 때도 있었지만, 여러 방을 동시에 볼 때는
놓치기 쉬워 웬만하면 손님에게 "지금 어떤 문제 풀고 계세요?"라고 직접 물어 진도를 확인했다.
(`PROGRESS_INFERENCE_THEN_CLARIFY`)

## 예외와 함정

- **"안 열리네", "왜 안 열려요" 류의 발화는 답답함이 아니라 기구 이상 신호일 수 있다.**
  겉으로는 힌트 요청처럼 보이지만, 실제로는 자물쇠 오작동이나 소품 이상인 경우가 많다.
  이런 발화는 감정 판단보다 먼저 원인부터 구분해야 한다: 정답 오류 / 자물쇠 오인 / 사용법 미숙 /
  실제 기구 이상. 기구 이상으로 판단되면 힌트가 아니라 즉시 게임마스터 호출(MASTER_REQUEST)로
  전환한다. (상태: ✅ 확정, `EQUIPMENT_AMBIGUITY`)

- **정답 요구에 진행자가 "말로" 직접 답해주면 문제가 된다.**
  현장에서 정답을 말로 직접 알려준 경우, 실제로 매니저에게 반복적으로 지적받았다.
  손님이 문제를 풀어 얻는 성취감이 게임의 핵심 가치인데, 진행자가 먼저 정답을 불러주면
  그 경험 자체가 사라지고 손님 만족도도 오히려 떨어진다. 그래서 매장은 "손님이 스스로 여는 탭"으로
  정답 확인 경로를 분리해, 진행자가 직접 불러주지 않으면서도 손님이 필요하면 확인할 수 있게 했다.
  → Agent도 이 방식을 따른다: 정답을 답변 텍스트에 먼저 꺼내 말하지 않고, 손님이
  직접 여는 별도 액션으로만 노출한다. (상태: ✅ 확정, `ANSWER_TEXT_GUARD`)

- **정답 요구·감정 신호·재요청 표현이 동시에 겹칠 수 있다.**
  예를 들어 약한 힌트 직후 재요청하면서 동시에 좌절 표현을 쓰는 경우, 결론은 강한 힌트로 같을 수
  있다. 이런 경우 결론이 같다고 조건을 아무거나 적당히 갖다 붙이지 말고, 실제로 어떤 조건이
  있었는지(정답 요구였는지, 감정 표현이었는지, 이력상 재요청이었는지)를 정확히 구분해서 남겨야
  한다. **재요청이라는 사실 자체가 자동으로 강도를 올리는 별도 규칙은 아니다** — LLM이 이력을 보고
  현재 발화의 의미를 종합 판단하는 재료 중 하나일 뿐이다. 나중에 이 판정이 맞았는지 틀렸는지
  되짚어볼 때, 조건이 뭉뚱그려져 있으면 어디를 고쳐야 할지 알 수 없다.

## 하지 말아야 할 것

- **정답(자물쇠 번호, 해답)을 응답 텍스트에 먼저 말로 꺼내지 않는다.** 정답 요구가 오면
  강한 힌트로 즉시 응답하되, 정답 자체는 손님이 직접 여는 별도 확인 액션(탭)으로만
  노출한다. Agent가 먼저 "정답은 OOO입니다"라고 말하지 않는다. (`ANSWER_TEXT_GUARD`)
- **감정 표현만 보고 섣불리 판단하지 않는다.** "모르겠다"는 표현 하나만으로 강한 힌트로 승격하지
  않는다. 시간·반복 시도 언급이 함께 있는지 반드시 같이 본다. (`FRUSTRATION_CONTEXT`)
- **기구·소품 이상 의심 상황을 힌트로 대응하지 않는다.** "안 열린다", "이미 풀려있다" 같은 발화는
  힌트 판단 이전에 원인부터 구분하고, 실제 이상이 의심되면 즉시 게임마스터에게 넘긴다.
  (`EQUIPMENT_AMBIGUITY`)
- **다른 테마의 문제나 힌트를 조회하거나 노출하지 않는다.** 세션 시작 시 고정된 테마 데이터만
  조회하도록 강제한다. (`SESSION_THEME_ISOLATION`)
- **아직 도달하지 않은 순서의 문제에 대한 질문에 먼저 답하지 않는다.** 스포일러 방지를 위해
  순서부터 안내한다. (`PUZZLE_POSITION_METADATA_PRIVATE`)
- **문제 번호나 전체 문제 개수를 손님에게 직접 알려주지 않는다.** 문제 번호(순서)를 알면
  그 순서대로 찾아서 풀 수 있게 되어 탐색·추리의 재미가 사라진다. "몇 번째 문제인지",
  "이 테마는 총 몇 문제인지"는 내부 관리용 정보이며, 힌트 응답에는 문제 번호 없이
  힌트 내용만 담아 전달한다. 진도 확인이 필요할 때도 손님에게는 "지금 하고 있는 문제"
  식으로만 언급하고 번호를 말하지 않는다. (`PUZZLE_POSITION_METADATA_PRIVATE`)
- **승인되지 않은 힌트를 새로 만들어내지 않는다.** 힌트 본문은 승인된 WEAK/STRONG 데이터만
  사용하고, LLM이 그 자리에서 새 힌트나 정답을 지어내지 않는다. (`APPROVED_HINT_ONLY`)
- **손님 요청만으로 진도나 타이머를 직접 바꾸지 않는다.** 시간 연장은 Agent가 즉석에서
  승인하지 않고 직원 요청으로만 전달한다. (`NO_DIRECT_PROGRESS_OR_TIME_CHANGE`)
- **숫자 기반 힌트 강도 규칙과 재요청 자동 승격을 실행 기준으로 인용하지 않는다.** 팀 검토 후
  채택하지 않기로 결정됐다(위 "판단 기준" 참고). 코드·프롬프트 어디에도 실행 로직으로 넣지 않는다.
  (`NUMERIC_HINT_STRENGTH_RULE`, `AUTO_REREQUEST_ESCALATION`)
