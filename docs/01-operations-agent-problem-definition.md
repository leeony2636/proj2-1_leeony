## 1-1. 한 문장 정의

방탈출 카페에서 발생하는 고객 요청, 힌트 제공, 장비 이상, 게임마스터 호출과 운영 기록을 자연어 기반으로 연결하고, 세션 상태와 운영 정책에 따라 안전하게 처리하는 운영 보조 Agent.

LLM은 고객·직원 요청의 의도와 감정을 해석하고 응답 문장을 생성한다. 세션 상태, 진도, 힌트 강도, 정답 동의, 요청 상태, 장비·타이머 제어는 코드와 MCP 및 Adapter가 결정한다.

---

## 1-2. 사용자

| 구분 | 대상 |
| --- | --- |
| 고객 | 힌트, 장비 이상, 게임마스터 도움을 요청하는 방탈출 참가자 |
| 게임마스터 | 여러 방의 진행 상태와 고객 요청을 확인하고 처리하는 직원 |
| 매장 직원 | 장비 이상, 방 리셋, 현장 운영 업무를 처리하는 직원 |
| 매장 관리자 | 테마, 퍼즐, 운영 정책과 통계를 관리하는 담당자 |
| 사용 상황 | 게임 전·중·후 고객 요청, 장비 이상, 직원 업무 처리, 운영 현황 확인 |

---

## 1-3. 상황과 문제

방탈출 카페에서는 한 명의 게임마스터가 여러 방을 동시에 확인해야 한다. 고객 요청은 정해진 버튼이 아니라 “이거 고장난 것 같아요”, “다음 힌트 주세요”, “직원분이 와주세요”처럼 짧고 모호한 자연어로 들어올 수 있다.

| 상황 | 현재 행동 | 문제 |
| --- | --- | --- |
| 고객이 퍼즐에서 막힘 | 게임마스터에게 직접 힌트 요청 | 반복 업무가 증가하고 응답 기준이 달라질 수 있음 |
| 같은 퍼즐에 재요청 | 게임마스터가 이전 대화와 제공 힌트를 다시 확인 | 힌트 강도와 처리 기준이 일관되지 않음 |
| 장비 이상 발생 | 고객이 힌트 요청처럼 표현하거나 직원에게 구두 신고 | 장비 문제와 퍼즐 문제를 잘못 분류할 수 있음 |
| 여러 방 동시 운영 | 게임마스터가 방을 번갈아 확인 | 긴급 요청과 일반 요청의 우선순위 판단이 늦어질 수 있음 |
| 직원 교대 | 구두로 현재 상황을 전달 | 미처리 요청과 특이사항이 누락될 수 있음 |
| 게임 종료 후 회고 | 기억이나 수기 기록에 의존 | 퍼즐·장비·운영 개선에 필요한 데이터가 부족함 |
| 테마 운영 중 문제 반복 | 고객 반응과 장애를 개별적으로 확인 | 어떤 퍼즐·장비가 운영을 방해하는지 파악하기 어려움 |

**핵심 반복 업무**

> 고객의 자연어 요청을 운영 이벤트로 분류하고, 세션 상태와 정책을 확인한 뒤 힌트 제공·장비 신고·게임마스터 요청·운영 기록으로 연결하는 일.

---

## 1-4. 핵심 작업

1. 고객의 요청을 힌트, 장비 이상, 게임마스터 호출, 일반 문의로 분류한다.
2. 요청이 모호하면 현재 방·퍼즐·상황을 확인하기 위한 질문을 한다.
3. 세션 상태, 남은 시간, 진도, 현재 퍼즐을 조회한다.
4. 이전 힌트 제공 이력과 동일 요청 재시도 여부를 확인한다.
5. 코드 정책으로 WEAK 또는 STRONG 힌트 강도를 결정한다.
6. 승인된 힌트만 MCP를 통해 조회한다.
7. ANSWER는 기본적으로 고객 동의 절차를 거친 뒤 제공한다.
8. 장비 이상은 고객 요청과 분리해 게임마스터 요청 및 장애 이력으로 기록한다.
9. 게임마스터 직접 요청은 운영 요청 큐에 등록한다.
10. 게임마스터가 요청을 확인·처리·취소할 수 있도록 상태를 관리한다.
11. 게임 종료 후 힌트·장비·직원 요청 이력을 운영 요약으로 제공한다.
12. 테마별 퍼즐·장비·요청 통계를 통해 운영 개선 후보를 제시한다.

### 처리 원칙

```text
고객·직원 입력
  → LLM 의도·감정·대상 정보 구조화
  → 코드가 권한·세션·상태 확인
  → MCP가 퍼즐·힌트·이력 조회 또는 운영 요청 기록
  → 코드가 최종 정책과 상태 전이 결정
  → LLM이 승인된 결과를 사용자 친화적인 문장으로 표현
  → 고객·게임마스터 화면과 운영 이력에 반영
```

### 기술 제약

- RAG 사용 금지
- LangGraph 사용 금지
- LLM의 자유로운 힌트·정답 생성 금지
- 고객 Agent의 진도 임의 변경 금지
- LLM의 직접 타이머·장비 제어 금지
- P0는 LocalRuntime 기반으로 구현
- ERCC는 후속 Adapter로 확장
- 입장은 MVP에서 임시 `session_id` 방식으로 구현하고 QR은 후속 확장
- STT는 입력 Adapter로 연결하되 모델 학습·튜닝은 후속 단계로 둠

## 1-5. 성공 기준

| 지표 | 목표 |
| --- | --- |
| 고객 요청 분류 정확도 | 힌트·장비 이상·게임마스터 호출 평가셋 기준 측정 |
| 승인되지 않은 힌트 출력률 | 0% |
| 미래 퍼즐 정보 노출률 | 0% |
| STRONG 정책 위반률 | 0% |
| ANSWER 무동의 제공률 | 0% |
| 장비 이상 분기 정확도 | 평가셋 기준 측정 |
| 게임마스터 요청 중복률 | 멱등성 키 기준 0% |
| 요청 상태 불일치 | 허용하지 않음 |
| 운영 요약의 원천 데이터 오류 | 코드 집계값과 불일치하지 않음 |
| MCP 스키마 통과율 | 100% |
| API 응답 지연 | 로컬 환경 p50/p95 측정 |
| LLM 오류율 | timeout·429·5xx 유형별 측정 |
| 게임마스터 수동 분류 부담 | 기준 시나리오 대비 감소 여부 측정 |

### 검증 가능한 성공 조건

1. “장치가 안 돼요”가 일반 힌트가 아니라 `EQUIPMENT_ISSUE`로 분기된다.
2. “직원분이 와주세요”가 `GAME_MASTER_REQUEST`로 기록된다.
3. 현재 퍼즐보다 뒤의 퍼즐 정보가 반환되지 않는다.
4. 승인된 힌트가 없으면 LLM이 임의의 힌트를 만들지 않는다.
5. STRONG 힌트는 코드 정책 조건 없이 제공되지 않는다.
6. ANSWER는 유효한 동의 절차 없이 제공되지 않는다.
7. 세션이 종료되면 힌트와 운영 요청이 정상 정책에 따라 제한된다.
8. 동일 요청 재전송 시 중복 기록이 생성되지 않는다.
9. 게임마스터 요청은 `OPEN → ACKNOWLEDGED → RESOLVED` 상태를 따른다.
10. 운영 요약의 수치는 이벤트 저장소의 값과 일치한다.
11. RAG·LangGraph 관련 의존성이나 구현이 포함되지 않는다.

# 03. LLM과 코드 역할 분리표

| 업무 단위 | LLM이 판단·생성 | 코드·MCP가 결정·증명 |
| --- | --- | --- |
| 입력 검증 | 입력 의미 해석 | 필수 필드, 길이, ID 형식, 알 수 없는 필드 검증 |
| 요청 분류 | 힌트·장비 이상·게임마스터 호출·일반 문의 추출 | 요청 유형별 실제 처리 분기 |
| 감정·긴급성 | 답답함·불만·긴급 신호 추출 | 우선순위와 긴급 상태 최종 결정 |
| 대상 식별 | “저 자물쇠”, “3번 문제”를 후보로 해석 | 세션·테마·퍼즐 접근 권한 검증 |
| 세션 상태 | 판단 자료로 참고 | 활성·종료 상태, 남은 시간, 진도 계산 |
| 힌트 강도 | 고객 표현과 상황에 대한 후보 의견 | WEAK/STRONG 최종 결정 |
| 힌트 콘텐츠 | 승인된 문장을 자연스럽게 표현 | 승인 힌트 존재·버전·현재 퍼즐 일치 확인 |
| ANSWER 동의 | 동의 의도와 확인 문장 생성 | 동의 토큰·유효시간·1회 사용 여부 검증 |
| 장비 이상 | 장비명·증상·위치·요청 내용을 추출 | 장애 이벤트 생성과 게임마스터 알림 |
| 게임마스터 호출 | 호출 이유와 고객 상황 요약 | 요청 큐 등록과 상태 전이 |
| 운영 현황 요약 | 여러 방의 상태를 자연어로 요약 | 원천 세션 데이터 조회와 수치 집계 |
| 인수인계 | 처리 이력과 특이사항을 요약 | 원본 이력 조회와 권한 검증 |
| 통계 해설 | 이상 패턴과 개선 후보를 설명 | 통계 수치 계산과 데이터 범위 제한 |
| 재시도 | 오류 메시지의 의미 해석 보조 | timeout·429·5xx 재시도·백오프 결정 |
| 최종 응답 | 고객·직원용 문장 생성 | 상태·힌트 강도·민감 필드 최종 검증 |
| 진도 변경 | 변경 의도만 추출 | 게임마스터 또는 내부 이벤트만 변경 가능 |
| 장비·타이머 제어 | 수행하지 않음 | 정책 승인 후 Adapter가 실행 |

## 코드가 반드시 최종 결정해야 하는 항목

- 사용자·직원 권한
- 세션 활성 여부
- 팀·테마·퍼즐 접근 권한
- 남은 시간과 진도율
- WEAK·STRONG 힌트 강도
- STRONG 자동 제공 조건
- ANSWER 동의 상태
- 승인 힌트 존재 여부
- 장비 이상과 게임마스터 호출 기록 여부
- 운영 요청 상태 전이
- 중복 이벤트 여부
- 정답과 미래 퍼즐 정보 노출 여부
- 통계 원천 수치
- ERCC·장비 제어 실행 여부

| `get_master_requests` | 게임마스터 요청 큐 조회 |
| `update_master_request` | 게임마스터 요청 상태 변경 |

`mark_puzzle_solved`, 타이머 변경, 테마 배포와 같은 상태 변경 도구는 고객 Agent에 직접 노출하지 않는다.

# 04. 경쟁 조사

## 공통 테스트 시나리오

> “힌트를 몇 번 봤는데 아직 3번 문제가 안 풀려요. 자물쇠도 이상한 것 같아요. 강한 힌트 주세요.”

확인할 항목:

1. 힌트 요청과 장비 이상을 분리하는가?
2. 이전 힌트 이력과 현재 진도를 반영하는가?
3. STRONG 힌트 제공 조건을 정책에 맞게 적용하는가?
4. 승인되지 않은 힌트를 임의 생성하지 않는가?
5. 게임마스터 개입이 필요한 상황만 운영 큐로 분기하는가?
6. 고객에게 처리 상태를 안내하고 직원에게 요약 정보를 전달하는가?

## 우리 Agent의 차별점

| 차별화 영역 | 설명 |
| --- | --- |
| 대화형 운영 이벤트 변환 | 고객의 자연어·음성 요청을 힌트·장비 이상·게임마스터 요청으로 구조화 |
| 안전한 힌트 정책 | LLM이 강도를 결정하지 않고 코드와 승인 힌트 카탈로그가 결정 |
| 고객과 직원의 연결 | 고객 응답, 운영 큐, 게임마스터 처리 이력을 하나의 흐름으로 연결 |
| 운영 데이터 축적 | 힌트·장비·요청 이벤트를 테마 개선과 운영 통계에 활용 |
| 시스템 중립성 | LocalRuntime, ERCC, 예약·장비 시스템을 Adapter로 교체 가능 |
| 제한된 자동화 | 진도·정답·타이머·장비를 LLM이 직접 변경하지 않음 |

## 차별점 한 문장

> 우리 서비스는 단순히 힌트를 자동으로 보내는 시스템이 아니라, 고객의 자연어·음성 요청을 운영 이벤트로 해석하고 코드와 MCP가 세션 상태·힌트 정책·장비 신고·게임마스터 업무를 안전하게 연결하는 방탈출 카페 운영 보조 Agent다.

# 05. MVP 범위와 후속 확장

## MVP에서 구현할 것

- 고객 텍스트 요청 처리
- STT 입력 Adapter 구조
- WEAK / STRONG 힌트 제공
- ANSWER 동의 확인
- 세션·퍼즐·힌트 이력 조회
- 장비 이상 신고
- 게임마스터 호출
- 게임마스터 요청 큐
- 요청 상태 변경
- 최소 운영 현황 화면
- LocalRuntime
- FastAPI·FastMCP 계약 테스트

## 후속으로 확장할 것

- 테마·퍼즐 관리자 화면
- 힌트·테마 버전 관리
- 장비 이력과 점검 체크리스트
- 운영 현황 자연어 요약
- 게임 종료 리포트
- 테마별 운영 통계
- ERCC Adapter
- 예약·POS Adapter
- 다중 매장과 역할별 권한

## 최종 MVP 정의

> 고객의 자연어·음성 요청을 힌트·장비 이상·게임마스터 요청으로 분류하고, 세션 상태와 간단한 운영 정책에 따라 처리한 뒤 고객과 게임마스터에게 결과를 전달하는 운영 보조 Agent.
