## 1. 한 문장 정의

방탈출 카페의 고객 요청, 게임 진행, 힌트 제공, 장비 이상, 게임마스터 업무와 운영 기록을 연결해 매장 운영을 보조하는 AI Agent를 제공한다.

## 2. 문제 정의

방탈출 카페는 한 명의 게임마스터가 여러 방을 동시에 관리하는 경우가 많다. 고객 문의, 힌트 요청, 장비 이상, 직원 호출이 서로 다른 방식으로 들어오면 우선순위를 놓치거나 처리 이력이 남지 않을 수 있다.

현재 운영에서 해결하려는 문제는 다음과 같다.

1. 고객의 자연어 요청을 힌트, 장비 이상, 직원 호출, 일반 문의로 빠르게 분류하기 어렵다.
2. 여러 방의 남은 시간과 진행 상황을 동시에 확인하기 어렵다.
3. 힌트 제공 기준이 게임마스터마다 달라질 수 있다.
4. 장비 이상 신고와 일반 힌트 요청이 섞여 대응 우선순위가 불명확해질 수 있다.
5. 게임마스터의 처리 내용과 고객 요청 이력이 체계적으로 남지 않을 수 있다.
6. 테마별로 어떤 퍼즐에서 고객이 막히는지 운영 데이터로 확인하기 어렵다.

## 3. 목표 사용자

| 사용자 | 주요 목적 |
|---|---|
| 고객 | 힌트 요청, 장비 이상 신고, 게임마스터 호출 |
| 게임마스터 | 진행 중인 방과 고객 요청 확인, 요청 처리 |
| 매장 직원 | 장비 이상·방 리셋·현장 업무 처리 |
| 매장 관리자 | 테마 운영 상태와 요청·장애 통계 확인 |
| 본사/다중 매장 관리자 | 여러 지점의 운영 지표 비교 |

## 4. 서비스 범위

### 4.1 고객 지원

- 자연어 힌트 요청
- 음성 입력을 위한 STT 연계 지점
- WEAK / STRONG 힌트 제공
- ANSWER 제공 전 명시적 동의 확인
- 장비 이상 신고
- 게임마스터 직접 호출
- 요청 접수·처리 상태 안내

### 4.2 게임 운영 보조

- 진행 중인 방 목록 조회

- 최근 고객 요청 확인
- 요청 유형·우선순위 분류
- 게임마스터 요청의 접수·확인·처리·취소
- 교대 시 운영 특이사항 확인

### 4.3 설비·장애 관리

- 반복 장애 조회
- 후속 단계에서 점검 체크리스트와 ERCC 연계

## 5. 핵심 운영 흐름

```text
고객 입력
  ↓
FastAPI 요청 검증
  ↓
LLM 의도·감정·문장 구조화
  ↓
코드 기반 세션·권한·운영 정책 확인
  ↓
MCP 조회 또는 기록 도구 호출
  ↓
고객 응답·게임마스터 알림·운영 이력 저장
```

### 5.1 힌트 요청

```text
고객: "여기서 뭘 봐야 할지 모르겠어요."
  ↓
의도: HINT_REQUEST
  ↓
세션·현재 퍼즐·힌트 이력 조회
  ↓
코드 정책이 WEAK 또는 STRONG 결정
  ↓
승인된 힌트 조회
  ↓
힌트 제공 이력 기록
  ↓
고객에게 짧은 문장으로 응답
```

### 5.2 장비 이상

```text
고객: "장치가 눌러도 작동하지 않아요."
  ↓
의도: EQUIPMENT_ISSUE
  ↓
장비·방·퍼즐 정보 확인
  ↓
장비 이상 신고 기록
  ↓
게임마스터 요청 큐 등록
  ↓
고객에게 접수 상태 안내
```

### 5.3 게임마스터 직접 요청

```text
고객: "직원분이 직접 와주세요."
  ↓
의도: GAME_MASTER_REQUEST
  ↓
요청 우선순위 계산
  ↓
게임마스터 요청 등록

처리 상태를 고객에게 안내
```

## 6. MVP 범위

### 6.1 반드시 구현할 기능

- 고객 텍스트 요청 처리
- STT 입력을 받을 수 있는 API 구조
- 세션 조회
- 현재 퍼즐 조회
- 힌트 이력 조회
- 승인된 WEAK / STRONG 힌트 조회
- 힌트 제공 이력 기록
- ANSWER 동의 확인
- 장비 이상 신고
- 게임마스터 직접 요청
- 게임마스터 요청 큐
- 요청 상태 변경
- 게임마스터용 최소 운영 화면
- LocalRuntime 기반 실행
- FastAPI·FastMCP 계약 테스트

### 6.2 MVP에서 단순화할 기능

- 테마는 합성 데이터 1~2개로 제한한다.
- 퍼즐 힌트는 WEAK·STRONG 중심으로 제한한다.
- 자동 힌트 조건은 남은 시간과 현재 퍼즐 체류 시간 중심으로 단순화한다.
- 요청 우선순위는 일반·높음·긴급 세 단계로 제한한다.
- 장비 관리는 장애 신고와 처리 이력까지만 구현한다.
- 통계는 이벤트를 기록하고 기본 집계만 제공한다.
- STT는 Mock Adapter를 기본으로 하고 실제 모델 학습·튜닝은 후속으로 둔다.

### 6.3 MVP에서 제외할 기능

- 예약·결제·환불
- 회원·포인트·CRM
- 다중 매장 운영
- 실제 ERCC 장비 제어
- 자동 보상 또는 시간 연장
- LLM의 직접 진도 변경
- LLM의 직접 타이머 변경
- 외부 웹 검색 기반 힌트
- RAG
- LangGraph
- 자동 테마 생성
- 고급 매출·수익성 분석

## 7. LLM과 코드·MCP 역할 분리

| 영역 | LLM | 코드·MCP |
|---|---|---|
| 고객 발화 해석 | 의도·대상·감정 구조화 | 입력 검증 |
| STT 결과 처리 | 전사 문장의 의미 분석 | STT 오류·빈 입력 처리 |
| 힌트 강도 | 후보 제안 가능 | 최종 강도 결정 |
| 힌트 내용 | 승인된 문장 자연화 | 승인 힌트 조회·검증 |
| 세션 상태 | 해석에 참고 | 실제 상태의 단일 기준 |
| 진도 | 언급 내용 추출 | 진도 변경 여부 결정 |
| 정답 제공 | 동의 의도 추출 | 동의 토큰 검증·정답 공개 |
| 장비 신고 | 장비 이상 의도 분류 | 신고 기록·상태 전이 |
| 직원 호출 | 요청 유형·긴급성 분류 | 요청 큐 등록·처리 |
| 타이머·장비 | 수행하지 않음 | Adapter를 통한 승인된 제어 |
| 통계 | 요약 문장 생성 | 원천 이벤트 집계 |

## 8. 힌트 정책

```text
기본 상태: WEAK
조건 충족: STRONG 자동 제공
정답 요청: ANSWER_CONFIRM_REQUIRED
장비 이상·직원 호출: GAME_MASTER_REQUIRED
정보 부족: NEED_MORE_INFO
범위 밖: OUT_OF_SCOPE
도구 실패: TOOL_ERROR
```

### 자동 제공 원칙

- WEAK는 기본 힌트 요청에 제공한다.
- STRONG은 코드 정책 조건을 충족하면 자동 제공한다.
- ANSWER는 기본적으로 동의를 받은 후 제공한다.
- 남은 시간과 잔여 퍼즐 수를 고려한 ANSWER 자동 제공은 후속 정책으로 둔다.
- 승인된 힌트가 없으면 LLM이 새 힌트를 만들지 않고 게임마스터 요청 또는 오류로 전환한다.

## 9. 운영 요청 상태

```text
OPEN
  → ACKNOWLEDGED
  → RESOLVED

OPEN
  → CANCELLED
```

요청 유형은 다음으로 제한한다.

```text
HINT_REQUEST
EQUIPMENT_ISSUE
GAME_MASTER_REQUEST
GAME_END_REQUEST
OTHER_OPERATIONAL_REQUEST
```

## 10. 차별화 방향

기존 운영 소프트웨어가 예약, 게임 진행, 타이머, 매장 대시보드에 강하다면, 우리 Agent는 다음을 차별화 영역으로 삼는다.

1. 고객의 자연어·음성 요청을 운영 이벤트로 변환한다.
2. 힌트·장비 이상·직원 호출을 하나의 요청 흐름으로 연결한다.
3. 세션 상태와 운영 정책을 확인한 뒤 안전하게 응답한다.
4. LLM이 직접 운영 상태를 변경하지 않도록 역할을 분리한다.
5. LocalRuntime, ERCC, 향후 외부 시스템을 Adapter로 교체할 수 있다.
6. 고객 요청과 직원 처리 이력을 테마 개선 데이터로 축적한다.

## 11. 시스템 경계

```text
Customer UI / Game Master UI
              ↓
            FastAPI
              ↓
       Agent Orchestrator
       ├─ LLM: 해석·문장화
       ├─ Policy: 상태·강도·권한

          FastMCP Tools
              ↓
       LocalRuntime / Repository
              ↓
       Future Adapters
       ├─ ERCC
       ├─ 예약 시스템
       └─ 장비 시스템
```

## 14. 성공 기준

### 고객 관점

- 고객 요청이 의도에 맞는 유형으로 분류된다.
- 승인되지 않은 힌트나 정답이 노출되지 않는다.
- STRONG 힌트가 정책 조건에 맞게 제공된다.
- 장비 이상 신고가 정상적으로 접수된다.

### 게임마스터 관점

- 진행 중인 방의 상태를 한 화면에서 확인할 수 있다.
- 요청 우선순위를 확인할 수 있다.
- 고객 요청과 처리 결과가 이력으로 남는다.
- 장비 이상과 힌트 요청을 구분할 수 있다.

### 운영 관점

- 이벤트 기록으로 기본 운영 통계를 산출할 수 있다.
- 테마·퍼즐 데이터가 버전으로 관리된다.
- 외부 장비 연동 없이 LocalRuntime에서 전체 흐름을 시연할 수 있다.
